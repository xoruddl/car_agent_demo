# 차량 에이전트 설계

## 1. 역할

실제 차량의 TCU(통신 모듈)와 OTA 클라이언트를 흉내 내는 독립 프로세스다. 컨테이너 하나를 차량 한 대로 실행한다.

에이전트는 시작할 때 차량을 등록해 토큰을 받고, 주기적으로 체크인한다. 업데이트 대상이면 매니페스트를 받아 CDN에서 파일을 내려받아 검증·설치한다. 설치 결과는 로컬 상태에 남겼다가 다음 체크인의 `lastUpdate`로 보낸다.

```
차량 에이전트
  │ ① 등록: 토큰 발급
  ├──────────────────────────▶ OTA 서버
  │
  │ ② 체크인: 차량 상태 + lastUpdate
  ├──────────────────────────▶ OTA 서버
  │ ◀───────────────────────── 업데이트 대상 여부 + campaignId
  │
  │ ③ 매니페스트 요청
  ├──────────────────────────▶ OTA 서버
  │ ◀───────────────────────── 파일 메타데이터 + CDN 서명 URL
  │
  │ ④ 다운로드·검증
  └──────────────────────────▶ CDN
```

모든 통신은 차량 에이전트가 먼저 시작한다. 에이전트가 직접 통신하는 대상은 OTA 서버와 CDN뿐이다. API의 요청·응답 필드는 [api.md](api.md)를 따른다.

## 2. 현재 범위

| 포함 | 제외 |
|---|---|
| 등록 API로 차량 토큰 발급 | MQTT 푸시 |
| HTTP polling 체크인 | Range 이어받기, 속도 제한 |
| 매니페스트 기반 다운로드 | A/B 슬롯, 롤백 |
| 파일 크기·SHA-256·Ed25519 서명 검증 | 지수 백오프와 jitter |
| 단일 설치 위치 | 주행·배터리 설치 조건 |
| 다음 체크인의 `lastUpdate` 결과 보고 | 에이전트가 타기팅 조건을 판정하는 기능 |

차종, TCU 하드웨어 리비전, 지역, 현재 버전을 이용한 대상 판정은 서버의 책임이다. 에이전트는 이 값을 등록·체크인 요청에 실어 보낼 뿐이다.

## 3. 설정

| 변수 | 필수 | 기본값 | 설명 |
|---|---|---|---|
| `VEHICLE_ID` | 예 | — | 차량 고유 ID. 영문·숫자·`-`, 최대 64자 |
| `VEHICLE_MODEL` | 예 | — | 차종. API의 `model` 필드 |
| `HW_VERSION` | 예 | — | TCU 하드웨어 리비전 |
| `REGION` | 아니요 | 빈 값 | 차량 지역 |
| `ENROLLMENT_KEY` | 예 | — | 등록 API에만 쓰는 공통 등록 키 |
| `OTA_SERVER_URL` | 예 | — | OTA 서버 베이스 URL |
| `CHECKIN_INTERVAL` | 아니요 | `30s` | 서버가 `nextCheckInSeconds`를 주지 않을 때의 기본 체크인 주기 |
| `DATA_DIR` | 아니요 | `./data` | 상태·다운로드·설치 파일 경로. 컨테이너에서는 볼륨 `/data` |
| `INITIAL_VERSION` | 아니요 | `1.0.0` | 최초 기동 시 현재 설치 버전 |
| `MANIFEST_PUBLIC_KEY` | 예 | — | Base64로 인코딩한 32바이트 Ed25519 공개키. 매니페스트 서명 검증에 사용 |

`VEHICLE_ID`는 상태 파일 속 차량과 같아야 한다. 다르면 다른 차량의 볼륨을 잘못 연결한 것이므로 기동을 거부한다.

## 4. 등록과 토큰

컨테이너 또는 에이전트 프로세스가 시작할 때마다 등록 API를 호출한다. 성공하면 받은 차량 토큰을 메모리에만 보관하고, 체크인과 매니페스트 요청의 `Authorization: Bearer {vehicle-token}` 헤더에 사용한다.

토큰을 상태 파일이나 볼륨에 저장하지 않는다. 따라서 컨테이너 재시작, 프로세스 크래시 후 재기동, 컨테이너 재생성 때 토큰은 사라지며 새로 등록한다. 재등록은 서버가 기존 토큰을 폐기하고 새 토큰을 발급하는 정상 흐름이다.

체크인 또는 매니페스트 요청에서 `401 UNAUTHORIZED`를 받으면 토큰이 폐기됐거나 유효하지 않은 상태다. 에이전트는 다시 등록해 새 토큰을 받은 뒤 요청을 재개한다.

## 5. 영속 상태

`DATA_DIR/state.json`에 상태를 원자적으로 저장하고, 재시작 시 복구한다. 토큰은 이 파일에 넣지 않는다.

```json
{
  "vehicle_id": "veh-001",
  "current_version": "1.0.0",
  "state": "DOWNLOADING",
  "pending_update": {
    "campaign_id": "cmp-20261002-001",
    "target_version": "1.1.0",
    "file_size": 52428800,
    "sha256": "9f86d081...",
    "signature": "q8h3...Base64...==",
    "download_url": "http://cdn.example/firmware.bin?md5=xxx&expires=1791000000",
    "url_expires_at": "2026-10-02T05:15:00.000Z"
  },
  "last_update": null
}
```

| 필드 | 설명 |
|---|---|
| `vehicle_id` | 상태 파일의 주인인 차량 ID |
| `current_version` | 현재 설치된 펌웨어 버전 |
| `state` | `IDLE`, `DOWNLOADING`, `INSTALLING` 중 하나 |
| `pending_update` | 진행 중인 매니페스트 정보. `IDLE`이면 `null` |
| `last_update` | 다음 체크인에 보낼 직전 업데이트 결과. 결과가 없으면 `null` |

`last_update`에는 `campaign_id`, `result`(`SUCCEEDED` 또는 `FAILED`), 실패 시 `failure_reason`, 선택 항목인 `failure_detail`, `finished_at`을 저장한다. 체크인이 `200 OK`로 끝나면 서버가 결과를 기록한 것이므로 `last_update`를 지운다. 응답 전에 종료되면 결과가 남아 다음 체크인에 중복 전송된다. 서버가 같은 결과를 멱등하게 처리하므로 안전하다.

상태 전이는 항상 **다음 상태를 파일에 저장한 뒤** 다음 동작을 수행한다. 이 순서라야 컨테이너가 어느 지점에서 종료돼도 재시작 후 작업을 이어갈 수 있다.

## 6. 상태 머신

```
                    체크인에서 대상
IDLE ───────────────────────────────────────▶ 매니페스트 요청
  ▲                                                   │
  │                                      상태 저장: DOWNLOADING
  │                                                   ▼
  │                                             DOWNLOADING
  │                                            │          │
  │                               실패 결과 저장│          │검증 성공 후 상태 저장
  │                                            ▼          ▼
  │                                          IDLE     INSTALLING
  │                                                      │
  └────────────────────── 결과 저장 ─────────────────────┘
```

| 단계 | 하는 일 | 영속 상태 처리 |
|---|---|---|
| 기동 | 등록 API로 메모리 토큰을 발급받는다 | 토큰은 저장하지 않는다 |
| `IDLE` | `lastUpdate`를 포함해 체크인한다 | `200 OK` 후 전달한 `last_update`를 지운다 |
| 매니페스트 요청 | 대상이면 매니페스트와 CDN URL을 받는다 | 성공 시 `pending_update`를 채우고 `DOWNLOADING`을 저장한다 |
| `DOWNLOADING` | 파일을 받고 크기·해시·서명을 검증한다 | 성공 시 `INSTALLING`을 저장한다. 실패 시 실패 결과를 저장하고 `IDLE`로 전환한다 |
| `INSTALLING` | 검증한 파일을 설치 위치에 반영한다 | 성공 시 버전과 성공 결과를 저장하고 `IDLE`로 전환한다. 실패도 실패 결과를 저장하고 `IDLE`로 전환한다 |

다운로드 URL이 만료되거나 CDN 서명 검증이 실패하면 매니페스트를 다시 요청해 새 URL을 받는다. 서버가 매니페스트 요청 때 대상 여부를 다시 확인하므로, 더 이상 대상이 아니면 실패 결과를 만들지 않고 `IDLE`로 돌아가 다음 체크인을 기다린다.

### 재시작 시 동작

| 저장된 상태 | 재기동 후 동작 |
|---|---|
| 모든 상태 | 먼저 등록해 새 차량 토큰을 받는다 |
| `IDLE` | `last_update`가 있으면 다음 체크인에 전송하고 평소처럼 체크인한다 |
| `DOWNLOADING` | 부분 파일을 버리고 매니페스트를 다시 요청한 뒤 처음부터 내려받는다 |
| `INSTALLING` | 같은 입력으로 설치를 다시 수행한다. 설치기는 멱등이어야 한다 |

다운로드 중이던 URL은 재기동 시 만료됐을 수 있으므로 `DOWNLOADING` 상태에서는 저장된 URL을 재사용하지 않는다. 저장된 `campaign_id`로 매니페스트를 다시 요청해 새 URL과 메타데이터를 얻는다.

### 실패 사유

| 코드 | 발생 시점 |
|---|---|
| `DOWNLOAD_FAILED` | CDN 오류, 연결 끊김, 파일 크기 불일치, 재시도 초과 |
| `HASH_MISMATCH` | 받은 파일의 SHA-256이 매니페스트와 다름 |
| `SIGNATURE_INVALID` | Ed25519 서명 검증 실패 |
| `INSTALL_FAILED` | 설치 중 파일 오류 |

## 7. 로컬 파일 배치

```
DATA_DIR/
├── state.json                  # 영속 상태. 토큰은 저장하지 않음
├── state.json.tmp              # 원자적 저장용 임시 파일
├── downloads/<campaign_id>.bin # 다운로드·검증 대기 파일
└── firmware/current.bin        # 설치된 펌웨어
```

## 8. 부품 구성

```
cmd/agent/main.go ── 조립 ──▶ agent (상태 머신)
                               ├── state.Store       상태 로드·원자적 저장
                               ├── otaclient.Client  등록·체크인·매니페스트 요청
                               ├── downloader        CDN 다운로드·크기·SHA-256 검증
                               ├── verifier          Ed25519 서명 검증
                               └── installer         설치 시뮬레이션
```

`agent`는 각 부품을 인터페이스로 받는다. 테스트에서는 가짜 구현과 `httptest` 서버로 등록부터 설치 결과 저장까지 한 흐름을 검증한다.

## 9. 리소스 가이드

- 이미지: distroless/static 기반, 약 10MB 목표
- 메모리: 대당 수십 MB 이하. compose에서 `mem_limit`, `GOMEMLIMIT`로 상한 설정
- 테스트용 더미 펌웨어: 1~5MB 랜덤 바이트
- 컨테이너 로그는 `max-size`로 로테이션
